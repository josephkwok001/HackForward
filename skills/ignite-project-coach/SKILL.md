# IGNITE project coach

## Use this skill when

Use it for the problem statement, solution overview, user journey, use cases, pitch, deck structure, demo story, submission README, or any question about whether the idea is sufficiently grounded in the hackathon brief.

## Project context

The working product is a software-only Singapore scam-response assistant for a person already in a fast-moving impersonation-scam interaction. It should help the person decide what to do next, using official guidance and controlled human handoffs. It is not a generic scam education chatbot, a bank, a police-report replacement, or a promise of recovery.

## Core method

1. Identify one role and one specific moment of need.
2. Describe the need and insight in the person’s own language.
3. Attach dated evidence from an authoritative source or user research.
4. Run the technology-free test: would the problem still exist if agentic AI had never been invented?
5. Keep the problem statement free of models, agents, apps, dashboards, and features.
6. Write a separate solution overview that names planning, acting, adapting, and the human benefit.
7. Explain what a fixed workflow would miss: changing evidence, uncertainty, branching stages, or the need for a focused question.
8. Map the story to benefits, originality, effectiveness, technical quality, and presentation.

## Quality checks

Reject or rewrite statements that are:

- about “everyone” without a concrete role and moment;
- a disguised solution, such as “people need an AI agent to…”;
- unsupported by evidence;
- so broad that the team cannot test them;
- already fully solved by an existing service without a differentiated gap;
- written in language the affected person would not use.

For this project, the strongest moment is usually after the first suspicious contact and before—or immediately around—a requested transfer, when the person must choose a safe next action under pressure.

## Required output format

When reviewing an idea, return:

1. The revised problem statement.
2. The named person, moment, need, and insight.
3. The evidence still needed and its date/source.
4. The technology-free test result.
5. A separate solution overview.
6. The fixed-workflow gap that justifies an agentic approach.
7. The smallest testable MVP boundary.

Do not turn a problem-statement review into an implementation plan unless the user asks for it.

## Judging alignment

When shaping the deck, demo, or submission copy, map every claim to one of these criteria:

- **Benefits:** one person, one moment, one safer next action.
- **Originality:** the gap a fixed checklist misses—changing evidence, uncertainty, or stage-specific routing.
- **Effectiveness:** scenario set, baseline comparison, and what the demo will measure.
- **Technical quality:** typed state, bounded loops, official-source tools, and visible safety gates.
- **Presentation:** problem statement and solution overview stay separate; the demo shows plan, act, and adapt.

Keep the problem statement technology-free. Put models, graphs, and tools only in the solution overview.
